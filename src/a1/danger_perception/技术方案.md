# A1 危险源识别与定位模块技术方案

## 1. 目标

本模块的目标是：让 Unitree A1 机器人在仿真楼栋中，通过自身传感器发现危险源，并输出危险源在比赛要求坐标系下的位置。

在当前比赛环境中：

- 危险源是红色球体，半径约 `0.15 m`。
- 干扰物包括红色方块和绿色球体。
- 最终结果需要写入 `results/detected_danger.json`。
- 最终位置必须是 Gazebo `world` 坐标系下的三维坐标 `[x, y, z]`，单位为米。

本文档只讨论 `a1/danger_perception` 及其上下游接口。最终 JSON 文件建议由 `a1/result_manager` 负责写入，危险源识别模块只负责发布结构化检测结果。

## 2. 用最简单的话理解这个问题

RealSense 相机看到红球时，算法一开始只能知道：

```text
红球在相机画面里的哪个位置
红球离相机大概多远
```

这属于“相机坐标”或“机器人相对坐标”。

但比赛评分需要的是：

```text
红球在整个 Gazebo 世界中的位置
```

所以完整流程必须包含两件事：

1. 识别：从图像里找到红色球体，并排除红色方块、绿色球体。
2. 定位：把相机看到的相对位置转换成 `world` 坐标。

其中第 2 件事依赖定位模块。没有定位模块时，危险源识别模块无法可靠知道红球在世界坐标系下的位置。

## 3. 重要坐标系

常见坐标系可以理解为：

| 坐标系 | 含义 |
|---|---|
| `real_sense_optical_frame` | RealSense 相机光学坐标系，图像和深度数据通常在这个坐标系下 |
| `real_sense` | RealSense 相机本体坐标系 |
| `base` | 机器人基坐标系，可以理解为机器人身体中心附近 |
| `odom` | 机器人局部里程计坐标系 |
| `map` / `world` | 全局坐标系，最终结果需要输出到这里 |

理想转换链路是：

```text
real_sense_optical_frame
  -> real_sense
  -> base
  -> odom
  -> map/world
```

其中：

- `real_sense_optical_frame -> base` 来自机器人模型的静态 TF。
- `base -> odom -> map/world` 需要定位模块提供。
- 正式比赛不能依赖 `/Odometry_gazebo` 或 `/ground_truth/*`，这些是裁判/调试专用真值通道。

## 4. 模块边界

建议把危险源相关功能拆成 3 个层次：

```text
a1_danger_perception
  负责图像识别、深度定位、坐标转换、发布检测结果

a1_result_manager
  负责汇总检测结果、去重、过滤、写 results/detected_danger.json

a1_localization
  负责提供机器人在全局坐标系下的位置和 TF
```

这样拆的原因是：识别算法会频繁调参，结果文件格式比较稳定，定位又是另一个复杂问题。拆开后各模块互不干扰。

## 5. danger_perception 内部子模块

### 5.1 传感器输入模块

职责：订阅 RealSense 图像、深度图和相机内参，并保证它们时间上基本对应。

输入：

```text
/real_sense/rgb/image_raw
/real_sense/rgb/camera_info
/real_sense/depth/image_raw
/real_sense/depth/camera_info
```

可选输入：

```text
/real_sense/depth/points
```

输出给内部算法：

```text
同步后的 RGB 图像
同步后的深度图
相机内参 fx, fy, cx, cy
图像时间戳 stamp
相机坐标系 frame_id
```

建议实现：

- 使用 `message_filters.ApproximateTimeSynchronizer` 同步 RGB、深度和相机内参。
- 使用 `cv_bridge` 把 ROS 图像转成 OpenCV 图像。
- 第一版优先使用 `depth_image_raw`，实现更直观。

### 5.2 OpenCV 颜色与形状检测模块

职责：在 RGB 图像中找到可能的危险源，并排除干扰物。

输入：

```text
RGB 图像
```

输出：

```text
候选目标列表：
- bbox: 图像中的矩形框
- mask: 目标区域
- class_name: red_sphere / red_box / green_sphere / unknown
- confidence: 置信度
```

推荐传统工程方法：

1. 把 BGR/RGB 图像转换到 HSV 色彩空间。
2. 根据 HSV 阈值提取红色 mask 和绿色 mask。
3. 对 mask 做开运算、闭运算，去掉噪声和小洞。
4. 提取轮廓 `contours`。
5. 根据面积、长宽比、圆度、凸包等特征筛选目标。
6. 红色且接近圆形的目标作为危险源候选。
7. 红色但明显偏方的目标判为红色方块干扰物。
8. 绿色球体判为干扰物，不作为危险源输出。

常用特征：

```text
area                  轮廓面积
bbox_width/height     外接框宽高
aspect_ratio          宽高比
circularity           圆度，4*pi*area/perimeter^2
depth_valid_ratio     mask 内有效深度比例
depth_median          mask 内深度中值
depth_std             mask 内深度离散程度
```

第一版可以先只做：

```text
红色 mask + 面积过滤 + 圆度过滤
```

等能稳定框出红球后，再加入红方块和绿球排除逻辑。

### 5.3 深度定位模块

职责：把图像中的目标转换成相机坐标系下的三维点。

输入：

```text
候选目标 bbox / mask
深度图 depth_image
相机内参 CameraInfo
```

输出：

```text
real_sense_optical_frame 下的三维位置 [x, y, z]
```

计算方式：

```text
Z = 目标区域内有效深度的中值
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
```

其中：

- `(u, v)` 是目标中心像素坐标。
- `fx, fy, cx, cy` 来自 `/real_sense/depth/camera_info`。
- `Z` 是深度值，单位必须统一成米。

注意事项：

- 深度无效时不要输出目标。
- 目标太远、太近、深度跳变太大时降低置信度或丢弃。
- 不要只取中心一个像素的深度，建议取 mask 或 bbox 中心区域的深度中值，更稳定。

### 5.4 坐标转换模块

职责：把相机坐标系下的目标点转换到 `world` 坐标系。

输入：

```text
real_sense_optical_frame 下的目标点
/tf
定位模块提供的全局位姿或 TF
```

输出：

```text
world 坐标系下的目标点
```

正式依赖：

```text
a1_localization 提供 map/world -> odom -> base 的 TF
```

调试依赖：

```text
/Odometry_gazebo
```

重要说明：

- `/Odometry_gazebo` 只能用于本地调试，正式算法不能依赖。
- 如果定位模块尚未完成，危险源识别模块可以先输出相机坐标或 `base` 坐标，用于验证识别和深度定位。
- 等定位模块完成后，再把坐标转换到 `world`。

### 5.5 多帧融合与去重模块

职责：避免同一个红球被重复输出，也避免单帧误检直接进入结果。

输入：

```text
每帧检测到的 world 坐标候选目标
```

输出：

```text
稳定后的危险源目标列表
```

建议策略：

- 同一位置附近多次观测到的目标合并为一个 track。
- 距离小于 `0.4 m` 到 `0.8 m` 的目标可以暂时认为是同一个危险源。
- 目标被连续或多次看到后提高置信度。
- 单帧偶然出现、置信度低、深度无效、TF 失败的目标不要输出。

## 6. 模块输入输出总表

### danger_perception 输入

| 输入 | 类型 | 用途 |
|---|---|---|
| `/real_sense/rgb/image_raw` | `sensor_msgs/Image` | OpenCV 颜色与形状识别 |
| `/real_sense/rgb/camera_info` | `sensor_msgs/CameraInfo` | 图像内参 |
| `/real_sense/depth/image_raw` | `sensor_msgs/Image` | 目标深度 |
| `/real_sense/depth/camera_info` | `sensor_msgs/CameraInfo` | 深度相机内参 |
| `/tf`、`/tf_static` | TF | 相机坐标到机器人坐标、机器人坐标到全局坐标 |
| 定位模块输出 | Odometry / TF / 状态 | 判断是否能输出 world 坐标 |

### danger_perception 输出

建议输出：

```text
/danger_perception/detections
```

内容包括：

```text
目标位置
坐标系 frame_id
类别 class_name
置信度 confidence
track_id
时间戳 stamp
```

建议同时输出调试话题：

```text
/danger_perception/debug/mask_red
/danger_perception/debug/mask_green
/danger_perception/debug/detections_image
/danger_perception/debug/candidates
```

这些调试话题可以帮助肉眼检查算法是否真的找到了红球。

## 7. 自定义消息的作用

自定义消息是模块间通信协议，不是识别算法本身。

例如危险源识别模块检测到：

```text
类别：红色球体
位置：[2.34, -1.56, 0.25]
坐标系：world
置信度：0.87
```

就通过 ROS topic 发布给其他模块。`result_manager` 订阅后，再负责最终写 JSON。

建议消息：

```text
# DangerDetection.msg
std_msgs/Header header
geometry_msgs/Point position
float32 confidence
string class_name
uint32 track_id
```

```text
# DangerDetectionArray.msg
std_msgs/Header header
DangerDetection[] detections
```

如果第一版想快速验证，也可以先用 `PoseArray` 或打印日志。但后续需要置信度、类别和去重 ID 时，自定义消息更合适。

## 8. 分阶段开发路线

### 阶段 1：只做图像识别

目标：只判断画面中有没有红球。

暂时不需要：

```text
world 坐标
定位模块
evaluate_danger.py
```

输入：

```text
/real_sense/rgb/image_raw
```

输出：

```text
/danger_perception/debug/detections_image
/danger_perception/debug/mask_red
```

验收方式：

- `rqt_image_view` 能看到 RealSense 原始画面。
- `detections_image` 能在红球周围画框。
- 红方块和绿球不会被当成危险源。

### 阶段 2：加入深度，得到相机坐标

目标：知道红球相对于相机的位置。

输入：

```text
/real_sense/rgb/image_raw
/real_sense/depth/image_raw
/real_sense/depth/camera_info
```

输出：

```text
red_sphere in real_sense_optical_frame: [x, y, z]
```

验收方式：

- 红球靠近时，深度值变小。
- 红球远离时，深度值变大。
- 坐标没有明显跳变。

### 阶段 3：临时使用 Gazebo 真值跑通 world 坐标

目标：提前验证坐标转换和评测流程。

临时输入：

```text
/Odometry_gazebo
```

输出：

```text
world 坐标下的危险源位置
```

说明：

- 这一阶段只用于本地调试。
- 代码结构上要留好接口，后续把 `/Odometry_gazebo` 替换成正式定位模块。
- 不要把 `/Odometry_gazebo` 当成最终方案。

验收方式：

```bash
python3 ./src/building_obstacles/scripts/evaluate_danger.py \
  --truth-file ./results/danger_truth.json \
  --detected-file ./results/detected_danger.json \
  --output-file ./results/evaluation_result.json \
  --verbose
```

### 阶段 4：接入正式定位模块

目标：不使用裁判真值，也能输出 `world` 坐标。

正式依赖：

```text
a1_localization
```

需要它提供：

```text
world/map -> odom
odom -> base
定位健康状态
```

验收方式：

- TF 树连通。
- 定位丢失时，危险源模块停止输出 world 坐标或标记 invalid。
- 同一个红球从不同角度看到时，world 坐标基本一致。

### 阶段 5：多帧去重和最终输出

目标：生成稳定结果，避免重复报警和误报警。

由 `a1_result_manager` 负责：

```text
订阅 /danger_perception/detections
过滤低置信度目标
空间聚类去重
记录探索时间
写 results/detected_danger.json
```

最终 JSON 格式：

```json
{
  "exploration_time": 98.76,
  "detected_danger_sources": [
    {"position": [2.34, -1.56, 0.25]}
  ]
}
```

## 9. 如何看图像和检测结果

启动只开 RealSense 的调试环境：

```bash
ENABLE_SENSOR_DATA=0 ENABLE_REALSENSE=1 GUI=true ./auto.sh
```

看 RealSense 原始图像：

```bash
rqt_image_view
```

选择：

```text
/real_sense/rgb/image_raw
```

也可以直接运行：

```bash
rosrun image_view image_view image:=/real_sense/rgb/image_raw
```

看算法画框后的图像：

```bash
rosrun image_view image_view image:=/danger_perception/debug/detections_image
```

看检测结果数据：

```bash
rostopic echo /danger_perception/detections
```

如果还没有自定义消息，第一版可以先打印日志或发布 `PoseArray`。

## 10. 如何让相机看到红球

仿真启动后，RealSense 不一定一开始就能看到红球。因为红球随机生成在房间里，而 RealSense 只看机器人前方。

调试方法：

1. 固定随机种子，减少变量。

```bash
SEED=1 DANGER_COUNT=1 DISTRACTOR_COUNT=0 ENABLE_SENSOR_DATA=0 ENABLE_REALSENSE=1 GUI=true ./auto.sh
```

2. 在 `junior_ctrl` 终端输入：

```text
2
4
```

3. 用键盘移动机器人：

```text
W/S 前后
A/D 左右
J/L 转向
空格停止
```

4. 同时看 `/real_sense/rgb/image_raw`，让红球进入画面。

本地调试时，也可以人工查看 `results/danger_truth.json` 找红球大概位置，但算法代码不能读取这个文件。

## 11. 调参建议

建议把参数写进 YAML，不要写死在代码里。

常见参数：

```text
hsv_red_low_1 / hsv_red_high_1
hsv_red_low_2 / hsv_red_high_2
hsv_green_low / hsv_green_high
min_area
max_area
min_circularity
min_depth_valid_ratio
max_depth_std
min_confidence
merge_distance
```

调参顺序：

```text
HSV 阈值
-> mask 形态学
-> contour 面积
-> 圆度
-> 深度有效率
-> 多帧去重距离
```

初始经验值：

```text
red hue: 0-10 和 170-180
green hue: 40-85
min_circularity: 0.65-0.75
min_depth_valid_ratio: 0.4
merge_distance: 0.5-0.8 m
```

这些不是最终值，需要根据仿真画面调。

## 12. 如何判断算法写得好不好

分阶段判断，不要一开始就追求最终分数。

### 12.1 图像识别阶段

看：

- 红球是否能被框出来。
- 红方块是否被排除。
- 绿球是否被排除。
- 远处小红点、墙面红色噪声是否误检。

工具：

```text
rqt_image_view
/danger_perception/debug/detections_image
/danger_perception/debug/mask_red
```

### 12.2 深度定位阶段

看：

- 深度是否有效。
- 目标相机坐标是否随距离合理变化。
- 深度跳变时是否被过滤。

### 12.3 world 坐标阶段

看：

- 输出 `frame_id` 是否是 `world`。
- 同一个红球从不同角度看到时，world 坐标是否基本一致。
- 机器人移动时，已经定位的红球坐标是否不会跟着机器人乱漂。

### 12.4 评测阶段

在能输出 `results/detected_danger.json` 后，用评测脚本检查：

```bash
python3 ./src/building_obstacles/scripts/evaluate_danger.py \
  --truth-file ./results/danger_truth.json \
  --detected-file ./results/detected_danger.json \
  --output-file ./results/evaluation_result.json \
  --verbose
```

重点看：

```text
correct        正确识别数量
missed         漏报数量
false_alarms   虚警数量
threshold_used 匹配阈值
```

## 13. 当前最现实的开发优先级

如果团队现在还没有完整定位模块，建议按下面顺序推进：

1. 完成 OpenCV 红球识别，输出画框调试图。
2. 加入深度图，输出相机坐标。
3. 本地调试时临时使用 `/Odometry_gazebo`，跑通 world 坐标和评测脚本。
4. 等 `a1_localization` 完成后，把 `/Odometry_gazebo` 替换成正式定位 TF。
5. 加入多帧去重和置信度管理。
6. 接入 `a1_result_manager` 写最终 JSON。

这样可以避免所有人都等定位模块完成后才开始做感知。

## 14. 风险点

1. 红球和红方块颜色一样，不能只靠颜色判断。
2. 深度图可能有空洞，不能只取一个像素。
3. 没有定位模块时，不能得到正式需要的 `world` 坐标。
4. `/Odometry_gazebo` 和 `/ground_truth/*` 只能用于本地调试，不能进入正式算法依赖。
5. 重复观测如果不去重，最终 JSON 可能有很多重复点，导致虚警率变高。
6. 只追求多报会降低虚警率得分，应该优先保证“红球报、干扰物不报”。

## 15. 最小可运行版本定义

最小可运行版本不要求完整自主探索，只要求：

```text
机器人看到红球
-> OpenCV 框出红球
-> 深度图给出相机坐标
-> 调试模式转换到 world 坐标
-> 发布检测结果
-> result_manager 写 detected_danger.json
-> evaluate_danger.py 能跑出结果
```

达到这个版本后，再逐步接入正式定位、导航、探索和任务管理。
